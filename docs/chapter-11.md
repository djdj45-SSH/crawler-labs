# 第 11 章 · 写防护：给自己的站起步

前面十章都在"攻"。这一章换到"守"，而且只回答一个问题：

> 我有一个自己的站，想加一层识别，**从哪一步开始、到哪一步该停**。

素材来自本项目的真实做法（博客 `blog.djdj45.top` 的反爬，
配置在 `crawler-dojo/tools` 里那份规则清单的同源版本，
以及 `crawler-dojo/cloudflare/README.md` 里两种实现与代价的对比）。

---

## 一、先回答三个问题，再动手

很多人一上来就想"怎么识别爬虫"。顺序错了。先问：

**1. 被爬了，我损失什么？**
   - 只是流量 → 大概什么都不用做
   - 服务器被压垮 → 需要限流，不需要拦截
   - 数据被抄走商用 → 需要识别 + 拒绝
   - 有人冒充我的站 → 这才是真的严重

**2. 我的站上有没有"不该被看见"的东西？**
   如果答案是没有（比如一个公开的技术博客），那么防护的目标就只是
   **省流量和减少噪音**，而不是"挡住谁"。目标不同，手段完全不同。

**3. 我愿意付什么代价？**
   误伤真人、多一跳延迟、每月多花几美元、还是每天花十分钟看日志？
   这一条决定上限。

本项目博客的答案：**公开技术博客，数据被抄无所谓，目标是不让"不声明身份的大规模抓取"
白白占用带宽，同时这件事本身有教学价值。** 所以它选的方案是最轻的那一档 ——
只对库默认 UA 做重定向，不通配、不限速、不拦真人。

---

## 二、识别维度：从便宜到贵

| 维度 | 成本 | 误伤风险 | 能被绕过吗 |
|---|---|---|---|
| User-Agent | 极低 | 低（只要规则写得窄） | 容易 |
| 请求路径模式 | 极低 | 中 | 容易 |
| IP / 频率 | 低 | **高**（NAT 后的真人互相拖累） | 中 |
| 请求头组合（`Sec-Fetch-*` 等） | 低 | 中 | 中 |
| JS 执行能力 | 中 | 低 | 需要浏览器 |
| 请求签名 / 令牌 | 高 | 低 | 需要拿到密钥 |
| TLS 指纹 | 高 | 低 | 贵 |

**起步永远从第一行开始。** 理由不是"简单"，而是**便宜的那一层已经能过滤掉
绝大多数噪音** —— 真正会做 TLS 指纹伪装的对手，本来也不是
一个个人博客需要考虑的对象。

反过来，如果你第一周就上 TLS 指纹，代价是你自己也会被挡在外面，
而且你还没建立起"正常流量长什么样"的基线。

---

## 三、正确的起步顺序

这是本章最想给的东西。四步，**每一步都可以单独停下来**：

### 第 0 步：先只看，不动手

在动手拦截之前，先让站跑一段时间，看日志里到底有什么。
没有基线，你无法判断一条规则是"挡住了爬虫"还是"挡住了读者"。

**这一阶段的目标产物是一句话**，比如"每天约 300 次请求，
其中 200 次来自同一个 UA 的固定路径扫描"。

### 第 1 步：白名单先行

**先写"谁能进"，再写"谁不能进"。**

顺序反了会出事：你先写了拦截规则，然后发现自己（或者搜索引擎）
也被挡住了，再去补白名单 —— 而这时候你站点在搜索引擎里可能已经被降权了，
而且要过几天才发现。

白名单里至少要放：
- 搜索引擎的 Verified Bot（这不是可选项）
- 你自己的爬虫（带联系方式的那种）
- 监控 / 拨测的 IP

### 第 2 步：最窄的黑名单

规则要窄到"我可以指着它说这是谁"：

```
http.user_agent contains "python-requests"
```

**不要**写成"不含 Mozilla 就拦" —— 那个规则会挡住一半以上的合法客户端，
包括各种 CLI 工具、老旧浏览器、无障碍阅读器。

本项目博客就是这么做的，而且只覆盖了几个明确的库 UA，一共 8 条规则。

### 第 3 步：限流（如果需要）

只有在第 0 步发现"确实有高频访问"时才做。限流是**唯一一种伪装没用的手段**，
但它也是**误伤最重**的（第 5 章在本地靶场上把这件事演示得很清楚：
你和爬虫同一个 IP，一开限流，你自己的浏览器也被挡）。

放到前面的位置，不要让它成为第一道。

## 四、误伤控制：这里最容易出事

三条具体建议：

**① 白名单要放在拦截之前，而且要有兜底出口。**
   一个"只靠黑名单"的配置，一旦规则写宽，你自己就进不去了。
   本项目所有的都是"重定向"而不是"封禁"，所以就算误判，损失也只是看到一张提示页。

**② 用 4xx，不要用 200 伪装。**
   返回 200 但内容不同 = Cloaking，搜索引擎会降权。
   除非你的规则窄到**真人永远不会命中** —— 本项目博客的规则就属于这种
   （只匹配库默认 UA），所以用 200 也是安全的。
   **但这是一条边界，不是一条常规。**

**③ 保留"能自己进去"的路。**
   本项目留了 `/__dojo/contract` 这类端点不带防护；
   博客那边留的是"声明身份的 UA 一律放行"。
   你需要一条不依赖规则正确性的后路。

## 五、代价：两种实现，差 10 万次/天

这一节是本章的技术核心。同一个"按身份返回不同内容"的需求，在
Cloudflare 上有两种实现，成本差一个数量级：

| | 边缘重定向规则 | Pages Functions 中间件 |
|---|---|---|
| 消耗每日配额 | **否** | **是**（每个命中请求 1 次） |
| 免费额度 | 10 条规则 | 10 万请求/天（与站上其他 Function 共用） |
| 能做有状态逻辑 | 否 | 是 |

**关键不是"哪个更强"，而是"配额是共享的"。**
如果站上还有一个基于 D1 的留言板，那么中间件烧掉的配额会让留言板先挂 ——
而且默认的 `fail open` 会让这种故障表现为"接口 404"，看起来像代码问题。

完整推演见 `crawler-dojo/cloudflare/README.md`。
一句话结论：**能靠边缘规则解决的，别用中间件。**

## 六、渐进式响应：比"一刀切"有效

不要只有"放行"和"拒绝"两个状态。真实站点的做法是分档：

| 档 | 触发 | 响应 |
|---|---|---|
| 0 | 白名单 | 正常内容 |
| 1 | 可疑但没证据 | 正常内容 + 记录 |
| 2 | 确认是自动化 | 挑战页 / 提示页 |
| 3 | 高频 | 限流（429 + `Retry-After`） |
| 4 | 持续高频 | 长时间限流 |
| 5 | 有攻击特征 | 拒绝 |

好处是每一步都可回退，而且**你能观察每一档的实际命中量**，
再决定要不要往下一档走。一刀切做不到这件事。

---

## 七、什么时候该停手

这一章最容易被忽略的一节。

**停止信号：**
- 你已经三轮都在调规则、但没再看日志了
- 你的规则误伤了真人（收到反馈，或者自己访问异常）
- 你在为"可能的攻击"加固，但第 0 步那天你根本没做
- 你的防护比你的内容还复杂

一个公开技术博客的正确终点，很可能就是本项目博客那样：
**8 条 UA 规则 + 一个提示页。** 再多就是在给自己的阅读体验加成本。

防护的目的是让站点可持续，不是赢一场对抗。

---

## 八、反面清单

照着做会出事，每一条都能在本项目里找到对应的讨论：

- ❌ 先写拦截、后写白名单
- ❌ 用 `200 + 假内容` 做通用伪装（Cloaking）
- ❌ 在 Pages Functions 里做无差别拦截（配额与留言板共用）
- ❌ 把 Pages 项目设成 `fail closed`（配额耗尽 → 全站 1027）
- ❌ 在中间件里对静态资源也做判断（每页多烧 4~5 次配额）
- ❌ 用频率限制作为第一道防线（误伤最重）
- ❌ 把防护规则提交进公开仓库当"文档"（等于开卷考试；
  但**规则的存在和原理**应该公开 —— 价值在"为什么这么配"）
