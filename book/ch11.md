## 11.1 写防护前的三个问题

**机制**

L1–L5 每一级拆开看，都是对三个问题的回答。你写防护前也应该先答它们：

| 问题 | L1 的回答 | L2 的回答 | L5 的回答 |
|---|---|---|---|
| **拦什么？** | 冒充浏览器的脚本 | 不守节奏的脚本 | "先抄 URL、之后再抓"的做法 |
| **误伤谁？** | 恰好用这些 UA 的正经工具 | 正常提速的用户 | 30 秒内没抓完的合规脚本 |
| **规则公开吗？** | 公开（黑名单 13 个） | 公开（5 次/10 秒） | 公开（密钥除外） |

第三个问题值得多想一步：**规则要不要公开？** 本书和靶场的立场是公开——
因为隐藏规则只对最弱的攻方有效（换个 UA 试三次就摸出来了），
而公开规则配合白名单，能让守规矩的爬虫**不需要试错**就能过。
你的博客就是活例子：robots.txt 里写着"本站欢迎爬虫，条件是它肯说明自己是谁"。

**博客的真实案例**（第 10 章你已经从攻方见过它）：
识别与改道发生在 Cloudflare 边缘（一条 302 重定向规则，不消耗函数配额）；
trap 页对搜索引擎声明 `Disallow: /traps/`，避免 Cloaking 风险；
白名单按 UA 里的联系方式放行。三层手段，每一层都能回答那三个问题。

## 11.2 `hmac.new()` —— 签名的零件

**它是什么**

```python
hmac.new(密钥字节, 消息字节, hashlib.sha256).hexdigest()
```

算一条消息的**带密钥指纹**：知道密钥的人才能算出来、才能验证。
和第 9 章的 `sha1()` 分工不同——sha1 只能证明"内容没改过"
（谁都能算），hmac 能证明"**是我们这边的人**发的"（只有持密钥者能算）。

**最小例子**

```python
import hashlib
import hmac

SECRET = "dojo-dev-secret"
msg = "/api/articles:1700000000"

sig = hmac.new(SECRET.encode(), msg.encode(), hashlib.sha256).hexdigest()
print(sig)
```

输出：

```
746d14c03a9e1482377529844d2a398d23294f4b0c8646dd2585dafa490efc3b
```

64 个十六进制字符（256 位 = 64 个 hex 位）。**换个输入试试**——
消息里时间戳差 1 秒：

```python
sig2 = hmac.new(SECRET.encode(), b"/api/articles:1700000001",
                hashlib.sha256).hexdigest()
print(sig == sig2)
```

输出：

```
False
```

输入差 1 秒，签名**面目全非**。这个性质叫雪崩效应，它是时间窗方案的根基。

**会怎么摔**

`hmac.new` 的参数吃**字节**不吃字符串——直接传 `str` 会得到
`TypeError: key: expected bytes or bytearray, got str`。
和第 9 章 hashlib 同一个坑：先 `.encode()`。
另外密钥别硬编码在生产代码里（靶场为了可教才公开它），
从环境变量或密钥管理服务读。

**你来试试**

改密钥再算一遍，确认签名也完全变了。
再算两次同样的消息——确认签名是**确定的**（同一输入永远同一输出），
这一点让它可以被服务端验证。

## 11.3 L5 四连 —— 签名绑定路径 + 时间窗

**实测**（按契约的规则：签名内容 `{path}:{ts}`，放进 `X-Dojo-Ts` / `X-Dojo-Token`）：

```python
import hashlib
import hmac
import time
import requests

BASE = "http://127.0.0.1:8000"
SECRET = "dojo-dev-secret"                 # 契约公开的教学密钥

def sign(path, ts):
    return hmac.new(SECRET.encode(), f"{path}:{ts}".encode(),
                    hashlib.sha256).hexdigest()

def call(path, ts, token):
    headers = {}
    if ts is not None:    headers["X-Dojo-Ts"] = str(ts)
    if token is not None: headers["X-Dojo-Token"] = token
    return requests.get(BASE + path, headers=headers)

now = int(time.time())
print("① 无签名      ", call("/api/articles", None, None).status_code)
print("② 正确签名    ", call("/api/articles", now, sign("/api/articles", now)).status_code)
print("③ 跨路径复用  ", call("/", now, sign("/api/articles", now)).status_code)
print("④ 过期签名    ", call("/api/articles", now - 90, sign("/api/articles", now - 90)).status_code)
```

输出：

```
① 无签名       403
② 正确签名     200
③ 跨路径复用   403
④ 过期签名     403
```

逐条读：

- **①** 403，`X-Dojo-Block: signature`——不签名寸步难行；
- **②** 200——签名正确且时间戳在 30 秒窗口内，放行，拿到的还是那 6 条真数据；
- **③** 是这一级的关键：签名是给 `/api/articles` 算的，拿去请求 `/`——
  签名内容里的路径对不上，服务端验签失败。**抄一个签名不能跨页面复用**；
- **④** 时间戳是 90 秒前的——超出 30 秒窗口，作废。

**你来试试**

把 ③ 的签名改成给 `/` 算的（`sign("/", now)`），确认变 200。
再把 ② 的时间戳加 29 秒、31 秒各试一次——亲手摸出窗口的边界。

## 11.4 签名该签什么 —— 守方的核心设计题

**机制**

11.3 的 ③ 和 ④ 不是两条随机的规则，是两个设计决定，各挡一种攻击：

| 签了什么 | 挡住的攻击 | 放过的攻击 |
|---|---|---|
| 只签时间戳 | 无签名乱打 | **30 秒内重放任意请求**（抄一个签名到处用） |
| 时间戳 + 路径（L5 方案） | 重放 + 跨页复用 | 改请求参数（参数没进签名） |
| 时间戳 + 路径 + **请求体摘要** | 上面全部 + 篡改内容 | ——（靶场没做，留作扩展） |

签名内容每多一项，抄走的签名用处就少一分。L5 方案挡住的典型对手是
**"先把 URL 清单列出来、之后再慢慢抓"**的做法——那份清单在 30 秒后
全部作废。它挡不住"边发现边抓"，那不是签名的事，是限流的事（L2）。
**每一级防一种坏，组合起来才叫防护**——单靠任何一级都会漏。

反过来检查你见过的所有真实 API：请求头里的 `Authorization`、签名参数、
时间戳、nonce……现在你能读出它"签了什么、防的是谁、漏了什么"。

**你来试试**

给 `sign()` 加第三个参数：把请求体（比如 `{"page": 1}`）也纳入签名
（拼进消息或单独算摘要）。改一个参数再签名——服务端必然 403。
想清楚：这个改动对**正常用户**的成本是什么？

## 11.5 什么时候停手 —— 反面清单

**机制**

防护的每一层都有成本，有些成本会反噬。下面这张反面清单，每一条
都对应真实世界踩过的坑：

- **对正常内容返回 200 的"换脸"**——按 UA 给不同内容是 Cloaking，
  搜索引擎降权伺候。trap 页要用 302/403/429 表达，并 `Disallow` 掉；
- **不给白名单出口**——只拦不放，守规矩的爬虫和恶意爬虫待遇相同，
  等于把"礼貌"这个选项从游戏里删掉；
- **fail closed**——防护层故障时全站拒绝服务。宁可 fail open（漏过去），
  也不要把"防护挂了"变成"网站挂了"；
- **在公开仓库里写死密钥**——规则可以公开，密钥公开等于没设防；
- **为 100% 拦截加码**——误伤成本最后由自己的真实用户支付。
  防护的目标不是"一个爬虫都进不来"，是"不守规矩的进不来"。

靶场的六级为什么是六级的量、不多不少——每一级都能回答 11.1 的
三个问题、都能通过这张反面清单。**能说清"我误伤谁"的防护，
才是可以上生产的防护。**

**你来试试**

用反面清单审查你自己：如果你的站点明天要上线，你会开哪几级？
把每一级对照三个问题和反面清单各写一句话理由——这份清单
就是你的第一份"防护设计文档"。

### 进阶（可选）

nonce（一次性随机数）是签名体系的下一块积木：服务端发给客户端一个
随机数，签名里带上它，用过即废——连 30 秒内的重放都防住。
想想它和时间窗是什么关系（重复防护？互补？），再想想实现它需要
服务端付出什么（存储、时效清理）。想明白这两问，你就可以去读
任何一家云服务商的 API 签名文档了——它们全是这套积木的变体。
