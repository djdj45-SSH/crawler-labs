# 第 5 章 · 429 与 Retry-After：被限速了

> **第二部分 身份：爬虫的自我介绍（2/3）**
> 上一章的失败指着鼻子告诉你"我是谁出了问题"。
> 这一章的失败不看你是谁——换什么 UA 都没用。
> 它只看一件事：**你有多快。** 这是"伪装"这条路走不通的第一个证据。

### 开工前

换挡：关掉靶场，用 L2 重起。

```bash
cd ../crawler-dojo
python -m server.main --level L2
```

契约里 L2 的规则：**10 秒窗口内最多 5 次请求**（`config: {"requests": 5, "window_seconds": 10}`）。

**本章必须对着活的靶场跑。** 限流是时间维度的现象——同一个窗口里
第 6 次才被拦。快照是"某一刻的一份响应"，它连"这是第几次请求"这个
概念都没有：把 429 冻下来，也复现不出"再多打一次就过了"。
这也是本书第一个**快照替代不了**的章节，实验里写了 `live_only` 并说明了理由。

## 5.1 连发 20 次，看第几次被拦

**90 秒现象**

写个循环，连发 20 次，把每次的状态码打出来：

```python
import requests

API = "http://127.0.0.1:8000/api/articles"

for i in range(1, 21):
    r = requests.get(API)
    print(f"{i:>2}  {r.status_code}")
    if r.status_code != 200:
        print("Retry-After:", r.headers.get("Retry-After"))
        print("X-Dojo-Block:", r.headers.get("X-Dojo-Block"))
        break
```

输出（**第几个数字会变**，取决于你机器的速度——跑之前先预测一下）：

```
 1  200
 2  200
 3  200
 4  200
 5  200
 6  429
Retry-After: 10
X-Dojo-Block: ratelimit
```

第 6 次——契约说 10 秒 5 次，第 6 次就是第一个出界的。
注意 `X-Dojo-Block: ratelimit`：上一章这个头还写着 `ua`（你是谁的问题），
现在写着 `ratelimit`（你多快的问题）。同一个信封，不同的拦截原因。

**429 的响应体**也是一页人话：

```
429 RATE LIMITED
这一级把你挡住了
拦截原因    10 秒窗口内已请求 5 次
响应头里带着 Retry-After: 10 —— 它在告诉你等多久。
```

**关键认知**：429 不是错误，是**协商**。对方在说"可以，但按我的节奏来"。
403 让你换身份，429 让你换节奏——听懂的人不需要对抗。

**你来试试**

连发 20 次并记下第几次被拦。等 10 秒再连发一次——被拦的位置一样吗？
（一样：窗口是滚动的，节奏才是自变量。）

## 5.2 `r.headers["Retry-After"]` —— 服务端在告诉你等多久

**它是什么**

```python
r.headers["Retry-After"]    # 字符串！"10"
```

429 响应里的标准头，语义是"**再等这么多秒，你的请求大概率能过**"。
它是整个 429 处理里最有价值的信息——**别自己猜，答案在信封上**。

**最小例子**

```python
r = requests.get("http://127.0.0.1:8000/api/articles")
if r.status_code == 429:
    wait = float(r.headers["Retry-After"])
    print("被限流，服务端让我等", wait, "秒")
```

输出（第几次被拦、等多久，每次都可能不同）：

```
被限流，服务端让我等 10.0 秒
```

**会怎么摔（本章摔跤点）**

两个坑都在这一行里。

坑一：**它是字符串**。`r.headers["Retry-After"] + 1` 会直接
`TypeError: can only concatenate str (not "int") to str`。
第 1 章说过 headers 全是字符串——这里是它最常咬人的一口。先 `float(...)` 再算。

坑二：**它可能不存在**。守规矩的服务端都会带这个头，但不是所有服务端都守规矩。
所以用 `.get()` + 判空，而不是直接取：

```python
wait = float(r.headers.get("Retry-After", 10))   # 没带就退回自己的默认值
```

**你来试试**

被限流后把 `Retry-After` 打出来，等几秒再打一次 429 的（如果还在被拦的话）——
观察这个数是不是在变小。想想它为什么会变。

## 5.3 `time.sleep()` —— 最笨也最有效

**它是什么**

```python
time.sleep(秒数)
```

让程序原地睡指定的秒数。爬虫的礼貌，一半是它给的。

**最小例子**（把 5.1 的脚本补完整）：

```python
import time
import requests

API = "http://127.0.0.1:8000/api/articles"

r = requests.get(API)
if r.status_code == 429:
    wait = float(r.headers["Retry-After"])
    print(f"被限流，睡 {wait} 秒……")
    time.sleep(wait + 1)          # +1 秒余量，别贴着线
    r = requests.get(API)

print("最终:", r.status_code, "条数:", len(r.json()))
```

输出：

```
被限流，睡 10.0 秒……
最终: 200 条数: 6
```

**为什么 +1 秒**

`Retry-After: 10` 是"再等 10 秒"，精确到秒——你的计时和对方的计时
之间总有毫秒级的误差。贴着线重试，很可能差 0.01 秒又吃一个 429，
而这个新的 429 可能**重置你的等待**。给余量是便宜又保险的事。

**你来试试**

把 `wait + 1` 改成 `wait`（不留余量）多跑几次，看看会不会偶发地
二次 429。礼貌这件事，余量就是表情。

## 5.4 指数退避 —— 等多久，为什么是指数

**它是什么**

一种重试策略：每次失败的等待时间**翻倍**——1s、2s、4s、8s……
写成一个通用函数，这是爬虫工程的标配零件：

```python
import time
import requests

def retry_get(url, max_tries=5):
    delay = 1
    for attempt in range(1, max_tries + 1):
        r = requests.get(url)
        if r.status_code == 200:
            return r
        if r.status_code == 429 and attempt < max_tries:
            print(f"  第 {attempt} 次重试前睡 {delay}s")
            time.sleep(delay)
            delay *= 2                     # 指数增长：1 → 2 → 4 → 8
    return r
```

**实测**（先把窗口打满，再交给它）——看时间轴：

```
打满窗口，当前状态: 429 Retry-After: 10
第 1 次重试（等 1s，距开始 1s）: 429
第 2 次重试（等 2s，距开始 3s）: 429
第 3 次重试（等 4s，距开始 7s）: 429
第 4 次重试（等 8s，距开始 15s）: 200
```

这张时间轴就是"为什么是指数"的答案：

- 固定 1 秒重试：10 秒窗口里你能撞 **10 次**墙，每次都刷新对方的计数器，
  而且每一次都是无效请求；
- 指数退避：1、3、7 秒时都还在窗口里（撞墙是**预期内**的），
  但 15 秒那次已经稳稳出了窗口。**指数增长意味着你用最少的尝试次数
  跨过任意长度的等待期**——窗口 30 秒也一样，再翻两倍就到了。

Retry-After 存在时优先听它的（5.3）；没有 Retry-After 的站点，
指数退避就是你唯一的策略。

**你来试试**

给 `retry_get` 加一个参数 `honour_retry_after=True`：收到 429 且响应头里
带 Retry-After 时，睡 `max(delay, retry_after)` 而不是自己的 `delay`——
两个策略取更礼貌的那个。

## 5.5 抖动 —— 比退避更重要的一件事

**机制**

假设一万个人用同一款爬虫软件，都撞上同一个限流窗口。如果大家都"指数退避、
精确 1s/2s/4s"——那么在 t=1s、3s、7s，服务端会收到**一万次齐步走的重试**。
退避解决了"单个客户端怎么等"，却制造了"所有客户端怎么一起等"的新问题：
**退避把洪峰拉长了，但没有打散。**

解法是在每次等待上加一点随机量，行话叫**抖动（jitter）**：

```python
import random

jittered = delay * (1 + random.uniform(0, 0.15))   # 上浮 0 ~ 15%
time.sleep(jittered)
```

一万个人现在会在 1.00s、1.07s、1.13s……各自醒来——洪峰在时间轴上被摊平。
本书实验套件里的退避实现就带着这一行：

```
退避  10.6 秒（建议 10 + 抖动）        ← 实验输出：10 秒建议值 + 随机上浮
```

**为什么说它比退避更重要**：单机场景下抖动看不出来；
但真实爬取几乎总是多实例、多任务并行的——**你的"多份副本"就是那一万个人**。
固定退避的副本们会齐步走，抖动的副本们各自走。代价是一行代码，收益是
"别人的限流墙不再因为你自己人撞自己人而更高"。

**你来试试**

给 5.4 的 `retry_get` 加上抖动。跑十次，观察每次"重试前睡 X 秒"
的数值——它们应该一次一个样。这个"不一样"就是你要的效果。
