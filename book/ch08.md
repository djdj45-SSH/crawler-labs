# 第 8 章 · Scrapy：框架帮你做了什么，又瞒了你什么

> **第四部分 工程：从脚本到项目（1/2）**
> 前七章你的爬虫是一个文件、几十行。能跑，但重跑要自己写循环、
> 限速要自己写 sleep、失败要自己兜。这一章把同一套逻辑搬进框架——
> 重点不是"学 Scrapy"，是看清楚**框架替你做了哪些决定**，以及
> 它替你做的决定里，哪几个和你想的不一样。

### 开工前

本章的工程在仓库的 `scrapy_dojo/` 目录，已经装好依赖（`pip install scrapy`）。
靶场可以开着（任意等级，白名单身份会跳过全部防护），也可以完全不开——
离线模式直接读快照：

```bash
cd scrapy_dojo
scrapy crawl articles -s DOJO_SNAPSHOT=auto     # 离线跑
scrapy crawl articles                            # 在线跑（需靶场开着）
```

## 8.1 工程长什么样

```
scrapy_dojo/
├─ scrapy.cfg                 # 入口声明：工程叫什么、settings 在哪
└─ dojo_spider/
   ├─ settings.py             # 全部决定：身份、限速、重试、管道顺序
   ├─ items.py                # 数据的形状（字段清单）
   ├─ spiders/
   │  ├─ articles.py          # 抓真数据（白名单身份）
   │  └─ honeypot.py          # 故意接假数据（裸身份，给校验管道喂料）
   ├─ middlewares.py          # 请求/响应的拦截层
   ├─ snapshot.py             # 离线模式：把快照接进框架
   └─ pipelines.py            # 校验 → 去重 → 落库 → 报告
```

对照第 2–7 章的手写脚本：`main.py` 里的"取页面 → 解析 → 校验 → 存储"
一个不少，只是每件事都搬进了框架指定的格子。**格子是框架的，思路是你的。**

## 8.2 Spider —— 入口方法与契约驱动

**它是什么**

Spider = 爬取计划：从哪个 URL 开始、拿到响应后产出什么。

```python
class ArticlesSpider(scrapy.Spider):
    name = "articles"
    snapshot_tag = "l0"

    def __init__(self, base_url=None, *args, **kwargs):
        super().__init__(*args, **kwargs)
        self.base_url = base_url or os.environ.get("DOJO_BASE_URL", "http://127.0.0.1:8000")

    async def start(self):
        contract = load_contract(self.base_url)          # 契约：路径与身份的唯一来源
        url = self.base_url + contract.endpoints["list_json"]
        yield scrapy.Request(url, headers=contract.whitelist_headers, cb_kwargs={"url": url})
```

两个值得停下来的点：

**入口方法是 `async def start()`，不是网上教程里的 `start_requests()`。**
Scrapy 2.13 起入口换成了异步的 `start()`，**2.19 里 `start_requests()`
已经完全不被调用**——实跑的现象是"Spider opened 之后立刻
Closing spider (finished)，0 个请求"，而且**不报任何错**。查
`scrapy/spidermiddlewares/start.py` 的源码，里面一次都没提到 `start_requests`。
这一条只有跑起来才会发现——这正是 8.5 的主题。

**端点和身份都来自契约，不硬编码。** `contract.endpoints["list_json"]`、
`contract.whitelist_headers`——哪天靶场换了路径或换了白名单 token，
这个 spider 一行不用改。第 4 章"开卷考试"的思路，在框架里照常成立。

## 8.3 Item 与 Pipeline —— 校验、去重、落库、报告

**Item**（`items.py`）是数据的形状声明。比 dict 好在：
字段拼错**立刻报错**，而不是安静地少一个字段。每个 item 还记了一个
`source` 字段（api / html / honeypot）——排查数据问题时第一个要回答的
就是"这条记录从哪个入口进来的"，这个信息不记就永远补不回来。

**Pipeline** 是 item 流经的关卡，顺序写在 settings 里：

```python
ITEM_PIPELINES = {
    "dojo_spider.pipelines.ValidationPipeline": 100,   # 校验
    "dojo_spider.pipelines.DupeBodyPipeline": 200,     # 去重
    "dojo_spider.pipelines.SqlitePipeline": 300,       # 落库
    "dojo_spider.pipelines.ReportPipeline": 900,       # 报告
}
```

**顺序即职责顺序**：校验必须在落库之前——脏数据一旦进了库，
你就得写清理脚本，而清理脚本自己也要校验，同一个问题做两遍。
校验的三条规则（必填字段 / 未来日期 / 字数虚标 3 倍）就是第 6 章
`check_batch` 的框架版——**同一套防线，换了个驻扎位置**。

实测（空库第一次跑）：

```
scrapy crawl articles -s DOJO_SNAPSHOT=auto

────────────────────────────────────────────────────
scrapy_dojo · articles（finished）
  通过校验     6 条
  入库         新增 6 · 更新 0
────────────────────────────────────────────────────
```

**紧接着再跑一次**（爬虫一定会重跑，这是"幂等"的定义时刻）：

```
scrapy_dojo · articles（finished）
  通过校验     6 条
  入库         新增 0 · 更新 6
────────────────────────────────────────────────────
```

`新增 0 · 更新 6`——slug 主键 upsert（第 9 章细讲）在框架里照样生效。
**再跑一遍 honeypot spider**，看校验管道拦的是什么：

```
scrapy crawl honeypot -s DOJO_SNAPSHOT=auto

────────────────────────────────────────────────────
scrapy_dojo · honeypot（finished）
  通过校验     0 条
  校验拦下     8 条，原因：
                 dojo-honeypot-01 — 未来日期 2026-10-04
                 dojo-honeypot-02 — 未来日期 2026-10-05
                 ……（8 条全部拦下）
  入库         新增 0 · 更新 0
────────────────────────────────────────────────────
```

第 6 章的结论在框架里原样成立：**8 条字段齐全的假数据，一条都进不了库。**

## 8.4 中间件 —— 在哪一层改请求

中间件是框架的"海关"：所有请求出境、所有响应入境，都要过它。
改请求头、看响应码、甚至直接伪造响应，都在这一层做。本工程用了两个：

```python
DOWNLOADER_MIDDLEWARES = {
    "dojo_spider.snapshot.SnapshotMiddleware": 540,      # 离线模式
    "dojo_spider.middlewares.DojoSignalsMiddleware": 585, # 信号统计 + Retry-After
}
```

**数字不是随便填的。** Scrapy 按数字排中间件的座次，而这两个数字
各有一个"跑了才知道"的理由：

- **540**：快照中间件要靠 UA 判断"我是谁"，而设置 UA 的
  `UserAgentMiddleware` 排在 500。排在它**前面**就只能读到空 UA——
  现象是"白名单身份也拿不到真数据"，而且没有任何报错把你往
  中间件顺序上引；
- **585**：信号中间件要赶在重试中间件（550）**之前**看到 429，
  好先把 Retry-After 的等待设好。而 `process_response` 是按数字
  **从大到小**调用的——所以它要比 550 **大**。同一张座次表，
  请求从小学号排队、响应从大学号排队，方向相反。

**离线模式**的实现只有一句话：下载器中间件允许在 `process_request`
里**直接返回一个响应**，从而跳过真正的下载——快照就是这个响应的来源。
spider、管道、校验逻辑一行不改。这本身就是"把响应当数据"的最好证明：
**离线快照不是某个脚本的取巧，它和框架无关。**

## 8.5 五个"跑了才知道"的框架行为

框架的价值是替你做决定，风险是**它做了你不知道的决定**。
以下是本工程实跑时真撞上过的五个，每个都标注了证据位置：

| # | 行为 | 现象 | 证据在哪 |
|---|---|---|---|
| 1 | `start_requests()` 已不被调用（2.19） | Spider opened → 立刻 finished，0 请求，**不报错** | `scrapy/spidermiddlewares/start.py` 里没有这个名字 |
| 2 | 重试码已含 429，但**不认识 Retry-After** | 它会重试，但不会等——三次重试在同一个窗口里撞完 | `scrapy/downloadermiddlewares/retry.py` 全文没提这个头 |
| 3 | 管道的响应处理**从大到小**、item 处理**从小到大** | 报告写在 close_spider 里会先于落库打印，出现"新增 0"的假象 | pipelines.py 的 ReportPipeline 注释 |
| 4 | AutoThrottle 不认识 429 | 被限流时它觉得"响应挺快"，继续催——还会覆盖 Retry-After 的延迟 | settings.py 的 AUTOTHROTTLE_ENABLED = False 注释 |
| 5 | 全局 USER_AGENT 会盖住"故意裸身份" | honeypot spider 忘了覆盖 UA 时，拿到的是**真数据**，信号头是空的 | spiders/honeypot.py 的 BARE_UA 注释 |

读法不是"背下这五条"——Scrapy 换个版本它们就会变。
要带走的是方法：**框架的行为 = 源码 + 实跑，缺一样都算猜。**
现象越"安静"（不报错、只是不对），越要往框架的隐藏行为上想。

**你来试试**

给 `ValidationPipeline` 加一条校验：正文长度小于 30 字符的拒收
（蜜罐正文恰好 66 字符，想想这条规则拦得住它吗？答案和第 9 章有关）。
跑 honeypot spider 验证你的改动。

### 过关检查

本章没有矩阵实验，跑通两条命令即过关：

```bash
scrapy crawl articles -s DOJO_SNAPSHOT=auto    # 报告：通过校验 6 · 新增/更新
scrapy crawl honeypot  -s DOJO_SNAPSHOT=auto   # 报告：校验拦下 8 · 入库 0
```

### 进阶（可选）

settings.py 里留了一道练习：继承 `AutoThrottleMiddleware`，
让它在响应码为 429 时**不要**覆盖 `slot.delay`——两者兼得：
按响应时间自适应 + 尊重 Retry-After。改完对着 `--level L2` 的靶场实测。
