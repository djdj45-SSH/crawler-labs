# 第 9 章 · 落地：数据要能重复入库

> 前八章都在解决"怎么拿到数据"。这一章解决"拿到之后怎么存得不后悔"。

## 9.1 `sqlite3` —— 一个文件就是一个库

**它是什么**

Python 标准库自带的 SQLite 驱动。SQLite 是一个**嵌在文件里**的数据库：
不需要装服务、不需要账号，`connect("文件名")` 就有了全部 SQL 能力。
练习和小项目用它，将来换 PostgreSQL 只改连接方式（9.5）。

**最小例子**

```python
import sqlite3

conn = sqlite3.connect("data/dojo.db")
conn.execute("""
CREATE TABLE IF NOT EXISTS articles (
    slug        TEXT PRIMARY KEY,
    title       TEXT,
    published_at TEXT,
    tags        TEXT,
    word_count  INTEGER,
    body        TEXT,
    body_sha1   TEXT
)
""")
conn.commit()
```

`IF NOT EXISTS` 让这段代码可以反复跑。注意主键：**`slug`，不是自增 id**。
slug 是站点给的自然键——同一个 slug 重复抓到就是同一篇文章，
用它去重比自增 id 有意义得多。`body_sha1` 这一列先记着，9.3 讲。

**会怎么摔**

`CREATE TABLE` 忘了 `conn.commit()`——不报错，但数据也没进去；
换一个连接去看，表不存在。sqlite3 的写操作（建表、插入、更新）
都要 commit 才落盘。读操作不用。

**你来试试**

建好表，用命令行或 Python 查一下 `sqlite_master`，确认表真的在。

## 9.2 幂等 upsert —— 跑两遍，结果一样

**它是什么**

"幂等"是个数学词，落到爬虫上就一句话：**同一批数据存几次，库里都是同样的内容**。
实现方式是 upsert：存在就更新，不存在就插入。

**错误姿势（先看它怎么坏）**

一个自然的想法是"入库前查正文重复"——第 6 章的防线嘛。但顺序错了：

```python
# ✗ 错误：正文查重放在了 slug 判断之前
if body_fingerprint in seen_bodies:
    rejected.append(a["slug"])     # ← 重跑时，真数据也会走到这里！
    continue
```

把这段代码对着真数据跑两遍，第二遍的输出是：

```
① 首次入库: (6, 0, [])
② 重跑一遍: inserted = 0  rejected = ['dojo-01-baseline', 'dojo-02-serial-framing',
   'dojo-03-crc-choice', 'dojo-04-thermal-drift', 'dojo-05-…', 'dojo-06-…']
   库里总数: 6
```

**重跑把 6 条真数据全部拒收了。** 原因：昨天的数据今天又抓到，
正文指纹当然重复——但那不是脏数据，是**你自己上次的劳动成果**。
（实验 11 的源码注释里记录了这个 bug 的第一版，一模一样。）

**正确姿势**

判断顺序决定一切：**先看 slug 在不在库里，再谈正文查重**。

```python
def store(conn, rows):
    # 已入库正文的指纹集合（注意：查的是 body_sha1 列，存的就是指纹）
    seen_bodies = {h for (h,) in conn.execute("SELECT body_sha1 FROM articles") if h}
    inserted = updated = 0
    rejected = []

    for a in rows:
        body = a.get("body", "")
        exists = conn.execute("SELECT 1 FROM articles WHERE slug=?",
                              (a["slug"],)).fetchone()
        if exists:
            # 已存在 = 自己上次抓进来的 → 更新，不做正文查重
            conn.execute("""UPDATE articles SET title=?, published_at=?, tags=?,
                            word_count=?, body=?, body_sha1=? WHERE slug=?""",
                         (a["title"], a["published_at"], ",".join(a["tags"]),
                          a["word_count"], body, fp(body), a["slug"]))
            updated += 1
            continue
        if fp(body) in seen_bodies:          # 只有新条目才查正文重复
            rejected.append(a["slug"])
            continue
        conn.execute("INSERT INTO articles VALUES (?,?,?,?,?,?,?)", ...)
        seen_bodies.add(fp(body))
        inserted += 1

    conn.commit()
    return inserted, updated, rejected
```

实测三连（`fp` 是下一节写的指纹函数）：

```
① 首次入库: (6, 0, [])
② 重跑一遍: (0, 6, [])          ← inserted=0 就是幂等
③ 灌 4 条同正文脏数据: (0, 0, ['dirty-0', 'dirty-1', 'dirty-2', 'dirty-3'])
库内总数: 6
```

三个数字各说各话：首次全插、重跑全更、脏数据全拒。
**判断"重复抓取"和"内容重复"是两件事**——前者用 slug（正常，更新），
后者用正文指纹（可疑，拒收）。混为一谈就是 9.2 开头那个 bug。

**你来试试**

把 6 条真数据连存三遍，确认 `inserted` 依次是 6、0、0。
然后把其中一条的 `word_count` 改掉再存——确认更新路径生效了。

## 9.3 `hashlib.sha1()` —— 正文的指纹

**它是什么**

```python
hashlib.sha1(字节串).hexdigest() → 40 位十六进制字符串
```

算一段内容的**指纹**：内容相同指纹必相同，内容差一个字指纹就完全不同。
第 6 章 F2 用它算过重复率，这里它上岗为**存储层的去重键**。

**最小例子**

```python
import hashlib

def fp(text):
    return hashlib.sha1(text.encode("utf-8")).hexdigest()

print(fp("同一篇文章"))
print(fp("同一篇文章"))
print(fp("同一篇文章。"))          # 多一个句号
```

输出：

```
21ec965afae0fe9ba0584dc451d10dd3769512fa
21ec965afae0fe9ba0584dc451d10dd3769512fa
e39ac61b1cf28e01a4e2f4d3f0e02e4dbcf41c04
```

（前两行相同因为输入相同；第三行完全不同——**差一个字，面目全非**。）

两个细节：`encode("utf-8")` 是因为 hashlib 吃字节不吃字符串；
比较指纹而不是比较原文，是因为指纹定长 40 字符，正文可能几万字——
**存得下、比得快**。这就是 9.1 表里 `body_sha1` 那一列的用途：
库里存指纹，新数据来了先比指纹。

**你来试试**

算一下第 6 章蜜罐那 8 条假数据的正文指纹——应该全部相同。
（这批数据 9.4 还会回来。）

## 9.4 拒收留痕 —— 不静默丢弃任何一条

**机制**

9.2 的正确版本把脏数据拒了，但如果只 `continue`，被拒的条目就**消失了**——
你会以为数据是完整的。**静默丢弃比不校验更危险。**

所以拒收要留痕：建一张 `rejected` 表，把每一条被拒的都记下来：

```python
conn.execute("""CREATE TABLE IF NOT EXISTS rejected (
    slug TEXT, reason TEXT,
    rejected_at TEXT DEFAULT (datetime('now')))""")

# 拒收时：
conn.execute("INSERT INTO rejected(slug, reason) VALUES (?, ?)",
             (a["slug"], "正文与已入库记录重复"))
```

实测 9.2 的 ③ 之后，rejected 表里躺着：

```
dirty-0  正文与已入库记录重复
dirty-1  正文与已入库记录重复
dirty-2  正文与已入库记录重复
dirty-3  正文与已入库记录重复
```

为什么这么较真？因为**这条规则会误伤**：两篇文章引用同一段长文，
是完全正当的写作行为。有留痕，误伤的可以人工复核、放行；
没留痕，你只能纳闷"为什么我的库里少了几篇文章"。

**你来试试**

把第 6 章蜜罐的 8 条灌进 `store()`（它们 slug 不同、正文相同）——
确认全部进了 `rejected` 表。第 6 章的读取层校验 + 本章的写入层校验，
两道闸都拦它，但拦的位置不同：**读取层拦了它就别浪费存储，
写入层是最后一道闸，防的是"校验有漏网"**。

## 9.5 存哪 —— CSV / JSON / SQLite 各自适合什么

**机制**（这一节没有新函数，是一张选型表）

| 格式 | 适合 | 不适合 |
|---|---|---|
| CSV | 给人看、给 Excel 打开、一次性导出 | 多层结构（tags 是列表就难受）、重跑去重 |
| JSON | 保留原始结构、程序间传递 | 要按字段查询、要更新某一条 |
| **SQLite** | 会重跑的爬虫、要按条件查、要事务 | 给 Excel 直接打开、跨机器共享 |

本仓库的正式实现（`storage/models.py`）用的是 SQLAlchemy——
一张表模型配四种连接串，SQLite、PostgreSQL、MySQL 换库只改连接串，
代码一行不动：

```
sqlite:///data/dojo.db                          ← 本地练习，零配置
postgresql+psycopg://user:pw@host/db            ← 生产
```

它还多了一张 `fetch_log` 表：每次抓取记下时间、URL、状态码、条数、身份。
**只存文章的话，出了问题你没法回答"这批数据是什么时候、用什么身份抓的"。**
抓取日志成本很低，但漏了就得重抓一遍才知道。

**你来试试**

给 9.4 的库里加一张 `fetch_log` 表，每次调 `store()` 前记一条。
跑两遍后查表——两行日志、库里 6 条，这就是"可追溯的幂等"。
